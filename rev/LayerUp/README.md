# LayerUp — VM / bytecode interpreter stage

The core of the final-binary stage: a custom bytecode VM plus the real
flag-check logic written *as bytecode*. The maze/unpacking and AES-CTR layers
are added in later sessions; for now the bytecode is embedded as a plain array
in `.rodata`.

## Files

| File             | Purpose                                                       |
|------------------|---------------------------------------------------------------|
| `interpreter.c`  | The VM. Function-pointer dispatch (no switch), one handler per opcode. |
| `assembler.py`   | Mnemonic → bytecode compiler. Emits `bytecode.h` for the C source. |
| `check.asm`      | The flag-check program: a single rolling accumulator over all input. |
| `bytecode.h`     | Generated by the assembler; `#include`d by `interpreter.c`.   |
| `check.bin`      | Optional raw bytecode dump (same bytes as the header).        |

## Build & test

```sh
# 1. assemble the bytecode program -> bytecode.h (and an optional .bin)
python3 assembler.py check.asm -o bytecode.h --bin check.bin

# 2. compile the VM (keep symbols while testing)
gcc -O2 -g -o interpreter interpreter.c

# 3a. correct input  -> "Correct!", exit 0
./interpreter 'SecurinetsENIT{t3st_t3st_1ay3r_up_th3_vm_cha1n_4a9f2c81_y0ufaaa}'

# 3b. anything else   -> "Wrong.", exit 1
./interpreter 'SecurinetsENIT{nope}'

# stdin works too (a single trailing newline is stripped):
printf 'SecurinetsENIT{t3st_t3st_1ay3r_up_th3_vm_cha1n_4a9f2c81_y0ufaaa}' | ./interpreter
```

For the shipped binary, strip symbols:

```sh
gcc -O2 -s -o interpreter interpreter.c     # or: strip interpreter
```

## Instruction set

Opcode bytes are deliberately scattered (not `0x01, 0x02, …`). Operands are
little-endian. Jump targets are **absolute** byte offsets into the bytecode.

| Mnemonic   | Byte  | Operand         | Effect                                            |
|------------|-------|-----------------|---------------------------------------------------|
| `PUSH imm` | 0x3C  | imm32 (4 bytes) | push imm                                          |
| `LOAD`     | 0x9A  | —               | pop idx; push `input[idx]` (0 if out of range)    |
| `LEN`      | 0x5E  | —               | push input length                                 |
| `ADD`      | 0x71  | —               | pop b,a; push a+b (mod 2³²)                        |
| `SUB`      | 0x24  | —               | pop b,a; push a−b                                  |
| `XOR`      | 0xB8  | —               | pop b,a; push a^b                                  |
| `MUL`      | 0x4D  | —               | pop b,a; push a*b (mod 2³²)                        |
| `ROL`      | 0xE2  | —               | pop c,v; push rotate_left(v, c)                   |
| `SHR`      | 0x53  | —               | pop c,v; push v >> c (logical)                    |
| `AND`      | 0x2F  | —               | pop b,a; push a&b                                  |
| `DUP`      | 0x17  | —               | duplicate top                                     |
| `SWAP`     | 0xCA  | —               | swap top two                                      |
| `POP`      | 0x66  | —               | drop top                                          |
| `CMP_EQ`   | 0x8F  | —               | pop b,a; push 1 if a==b else 0                    |
| `JZ addr`  | 0xD3  | addr (2 bytes)  | pop v; if v==0 jump to addr                        |
| `JMP addr` | 0x1B  | addr (2 bytes)  | jump to addr                                      |
| `HALT`     | 0x7B  | —               | pop verdict (1 == correct); stop                  |
| `STOREV s` | 0x42  | slot (1 byte)   | pop v; `var[s] = v`                               |
| `LOADV s`  | 0xAE  | slot (1 byte)   | push `var[s]`                                     |

VM state: a 256-entry `uint32` operand stack, 8 variable slots, a program
counter, and read-only access to the raw input buffer.

### Note on the instruction set

Your spec listed `PUSH, LOAD, ADD, SUB, XOR, MUL, CMP_EQ, JZ, JMP, HALT`. A
looping accumulator over *all* input bytes can't be expressed with just those —
it needs an actual rotate and some addressable loop state. So I added the
minimum to make the accumulator writable and readable:

- `LEN` — loop bound (`while i != len`), so inputs of the wrong length fail naturally.
- `ROL` / `SHR` — the rotate and the lossy truncation step the accumulator uses.
- `LOADV` / `STOREV` — 8 variable slots to hold `A`, `B`, `i`, and the current byte.
- `AND` / `DUP` / `SWAP` / `POP` — not used by the current `check.asm`, kept because
  they give Ghidra more handlers to chase and are handy for decoys.

If you'd rather keep the ISA minimal, drop `AND/DUP/SWAP/POP`; `LEN`, `ROL`, `SHR`,
and the two var ops are load-bearing for the current `check.asm`.

## The flag-check logic (dual accumulator, solver-required)

`check.asm` runs **two** rolling accumulators, `A` and `B`, over the entire input
in a single pass and compares only the **final** values — no per-byte comparisons
anywhere. Each round feeds the **high** bits of `A` (a lossy truncation) into `B`,
and the verdict requires *both* to match:

```
A = BASIS_A                       ; 0x7E4A1C3B
B = BASIS_B                       ; 0x2D5F8E11
for i in 0 .. len-1:
    A = A XOR input[i]
    A = rotate_left(A, R1)        ; R1 = 11
    A = A * MULT_A                ; 0xA3C59AC3 (odd -> bijective), mod 2^32
    A = A + i
    t = A >> SHIFT                ; SHIFT = 16  -- LOSSY: only A's high bits survive
    B = B + t * MULT_B            ; 0xCF1BBCDD
    B = rotate_left(B, R2)        ; R2 = 7
    B = B XOR input[i]
verdict = (A == TARGET_A) AND (B == TARGET_B)
```

### Why this needs a solver

The `A >> SHIFT` step throws away `A`'s low 16 bits each round, so the chain
**cannot be cleanly inverted backwards** — the information needed to step back is
gone. And because `B` is coupled to `A`'s high bits, the two targets can't be
satisfied independently. Recovering the input is therefore a constraint problem
(e.g. Z3 over the input bytes), not mechanical back-stepping. A charset-constrained
Z3 model recovers the flag in well under a second; see
`solve_poc.py` in your notes for a working proof-of-concept. (The constants are
arbitrary/non-recognizable, so there's no FNV-style pattern-match shortcut.)

`TARGET_A` / `TARGET_B` are **not** hand-written. The assembler's `.target <flag>`
directive runs this exact accumulator over the flag and defines both symbols — so
to change the flag you edit the `.target` line in `check.asm` and re-run the
assembler; the targets update automatically. (It prints them to stderr, e.g.
`TARGET_A = 0xA5219537, TARGET_B = 0xC19B6387` for the current flag.)

The reference accumulator in `assembler.py` (`accumulate()`) must stay
byte-for-byte equivalent to what `check.asm` executes — `BASIS_A/B`, `MULT_A/B`,
`R1`, `R2`, and `SHIFT` are `.def`'d once in `check.asm` and used both in the
`PUSH` instructions and in the `.target` computation, so they can't drift apart.

## Writing your own bytecode

The assembler understands:

```
; comment
label:                 a jump target (own line, or as a prefix to an instruction)
.def NAME value        define a constant (decimal / 0x-hex)
.target <flagstring>   compute TARGET_A/TARGET_B from the accumulator over <flagstring>
INSTR [operand]        one instruction per line; operand may be a number or symbol
```

```sh
python3 assembler.py check.asm -o bytecode.h    # C header to embed
python3 assembler.py check.asm --bin out.bin     # raw bytes
python3 assembler.py check.asm                   # hex dump to stdout
```

## Hooks for later stages

- **AES-CTR:** replace the plain `g_bytecode[]` in `bytecode.h` with the
  ciphertext, and decrypt into a RAM buffer in `run()` before the dispatch loop
  (point `vm.code` at the decrypted buffer). The AES-128 key is assembled from
  the maze key material.
- **Maze:** each layer contributes a few key bytes; only a fully-correct layer
  yields its bytes, and the single pass/fail verdict here is the only feedback in
  the whole chain.
